## Как устроено отключение FUSE

`tools/vold-fusefs.c` подменяет трамплин PLT в vold. Ставятся **два** хука —
`mount` и `umount2` — **вместе или никак**: хук только на `mount` ставит два
монтирования на `fuse_path`, а vold сносит одно, и получается FUSE-монтирование без
демона → `ENOTCONN` → том `unmountable` → приложения снова на FUSE.

Инвариант, который держит всё: **«один `umount2` очищает `fuse_path`»**.

- FUSE-монтирование **обязано** остаться живым: fd — часть контракта с демоном
  MediaProvider, без FUSE-суперблока демон не стартует и том уходит в `unmountable`.
  Bind `/data/media` кладётся **сверху** и делает всю работу.
- Доставка приложениям — **трансляцией**: bind ложится на `/mnt/user/<user>/emulated`
  (shared-маунт), а namespace приложения — слейв группы init, поэтому маунт приходит
  туда сам. Модулю монтировать нечего. `MS_REC|MS_PRIVATE` в namespace приложения эту
  связь рвёт — см. раздел об устранённой избыточности ниже.
- Путь распознаётся **по форме** (`/mnt/user/<цифры>/emulated`), не по
  запомненному значению — запоминать нечего, чистить при перезапуске vold нечего.
- `/system/etc/init/vold.rc` → `reboot_on_failure reboot,vold-failed`: смерть vold'а
  = перезагрузка, а патч ставится на каждой загрузке. Watchdog не нужен.

Подробный разбор задачи, AOSP-ссылки, аудит мест вызова `umount2` и протокол
проверки — в `memory/2026-10-07-fuse-off-root-fix.md`.

### Избыточность `attach()` — устранена 2026-10-07

Из `src/unfuse_zygisk.cpp` убраны `unshare(CLONE_NEWNS)`, `MS_REC|MS_PRIVATE` на `/`
и все `attach()`. Осталось ровно одно действие — `mount_storage_dirs = JNI_FALSE`.

Почему это оказалось не «две независимые вещи», а одна самоподдерживающаяся пара:
приватность ставилась, чтобы bind модуля не утёк в zygote, а она же **обрывала
slave-связь**, через которую до namespace доходит bind vold. Замеры
(`/proc/<pid>/mountinfo`, устройство `marble`, Android 16):

| форма namespace | маунты vold |
|---|---|
| создан до маунта, слейв/пир (тест `unshare -m` + `mount --make-slave /`) | получает трансляцией: 0 → 2 |
| слейв `master:1` (`com.android.settings`, модуль не трогает) | имеет и **теряет** вместе с томом — следит |
| приватный (`com.termux`, `com.android.systemui`) | **не** получает; держит замороженную копию |

Решающий опыт: `sm unmount emulated;0` и снимок **внутри окна**. У `settings` на точке
0 маунтов, у `termux`/`systemui` — всё на месте. То есть приватный namespace живёт
своей копией и за vold не следит.

Отсюда вывод, ради которого всё делалось: **у `systemui`/`launcher3` модульный bind
был не «несущим», а единственным следствием приватности** — они специализируются
раньше, чем vold смонтирует том, и приватность не пускала маунт внутрь. Убрать bind,
оставив приватность, — сломать их. Убрать и то и другое — вернуть им форму `settings`.

**Грабли: mount id переиспользуются ядром (низший свободный), поэтому совпадение id
до и после цикла тома ничего не доказывает.** Судить только по снимку внутри окна.

Цена: вместе с блоком ушло плечо `/mnt/runtime/<view>/emulated` — оно нужно только
pre-FUSE-форме Android 11/12/12L/13 (`persist.sys.fuse` не true), где `Zygote` биндит
`/mnt/runtime/<view>` на `/storage`. `MountUserFuse()` монтирует только под
`/mnt/user/<user>` (`Utils.cpp:1600-1602`), а `/mnt/runtime/<view>` — место sdcardfs
(`EmulatedVolume.cpp:360-363`). На 14+ плечо не работало: здесь `persist.sys.fuse=true`,
то есть `zygote_uses_runtime_view()` уже была false.

Изменение **активировано на устройстве 2026-10-07** (установлено `install.sh`,
zygote перезапустился и загрузил новый `.so`; перезагрузки не было, `boot_id` тот же).
Регресса по хранилищу нет: 824/824 процесса на f2fs, четыре дерева 2/2/2 и 1, оба
патча rc=0, logcat чист. Новый код подтверждён поведенчески: приложение в обычном
`DEFAULT`-режиме видит **51** запись в `Android/data` (столько же, сколько сырое
дерево), tmpfs над `Android/data` нет.

Устаревшие комментарии: **исправлены 2026-10-07** — `build.sh:5` («Builds three

## Проверка (обязательный минимум)

Патч нельзя считать рабочим по одному удачному монтированию. Минимум:

1. `--check` → `оба патча уже стоят ("mount" и "umount2")`, rc=0.
2. Циклы `sm unmount`/`sm mount`: **счётчик монтирований** 0 после снятия, 2 после
   монтирования (fstype проверять только после монтирования).
3. Все **четыре** дерева: `/mnt/user`, `/mnt/installer`, `/mnt/androidwritable`
   (n=2, f2fs сверху) и `/mnt/pass_through` (**n=1**, f2fs — там FUSE нет).
4. logcat без `Transport endpoint is not connected` / `Failed to mount emulated fuse`.
5. **Каждое** приложение (без фильтра по uid — `com.android.settings` работает как
   uid 1000): резолвить путь **внутри** его пространства имён через
   `/proc/<pid>/root/storage/emulated/0` и требовать `f2fs` **и** совпадения
   `dev:ino` с `/data/media/0`. Наличие строки `fuse` в `/proc/<pid>/mounts` —
   **норма**, это нижний слой; порядок в `/proc/mounts` не является порядком
   наложения, поэтому судить по нему нельзя.
6. **Состояние модуля:** `once` в `/data/adb/unfuse_zygisk.state` существует, метка
   каталога `magisk_file`, старых путей в `/data/adb` нет. Строку `UnfuseZygisk` в
   логе **нельзя** искать «просто так»: кольцевой буфер на устройстве короткий
   (≈35–42 тыс. строк, минуты), и к моменту проверки загрузка уже прокручена.
   Сэмпл воспроизводится так: `logcat -b all -c`, `rm -f …/state/once`, перезапуск
   любого приложения — модуль печатает сэмпл заново (это ровно состояние после
   загрузки). Ожидаемый текст: `домен u:r:zygote:s0` + вторая строка с отчётом о
   патчах libc. Отсутствие сэмпла при существующем `once` — **не** дефект модуля.
7. **Активна ли новая сборка:** сверить inode файла на диске с `ino=` строки
   `unfuse_zygisk 64` в `/data/adb/zygisksu/modules_info` (совпадение = демон
   переоткрыл файл, сборка живая). Поле `sz` там — **не размер файла**, сравнивать
   по нему нельзя. Выключатель проверяется только так: снять `once` **и** положить
   `no_hooks` → первая строка скажет `хуки выключены файлом`, строк `хуки libc в uid`
   должно быть 0; после снятия `no_hooks` — снова `хуки включены` + отчёт.

## Установка `.so` на живое устройство — только атомарно

**Никогда не перезаписывать `zygisk/*.so` через `cp -f` на работающей системе.**
`cp -f` усекает файл и пишет по частям **в тот же inode**, а `.so` отображён (mmap)
в zygote и во все его потомки. Замеренная расплата (2026-10-07, установка руками):

- **SIGBUS `BUS_ADRERR`** в `zygote64` — подпись усечённого файла под живым mmap;
- **SIGSEGV `SEGV_MAPERR` ровно по `0x34820`** в приложениях — это файловый офсет
  `.plt` нового `.so`, он же значение в `.got.plt` на диске (плейсхолдер ленивого
  связывания = `plt0`). Падающий кадр — инструкция `bl <...>@plt`; процесс уходит в
  `br x17`, где `x17` = **сырое файловое** значение, потому что релокации
  `R_AARCH64_JUMP_SLOT` к слоту не применились (линкер читал недописанный файл);
- zygote'ы рождаются и умирают с `Process uptime: 1s/2s`; `system_server` падает
  («Lost network stack») и перезапускается; `sensor-notifier` получает SIGABRT
  `DEAD_OBJECT` — уже как следствие.

Диагностический признак, по которому это узнаётся: **адрес падения равен файловому
офсету целой секции** (`.plt`) и **лежит на диске в `.got.plt`**. Проверять так:

```
od -A x -t x8 -j $((0x3c040)) -N 8 module/zygisk/arm64-v8a.so   # слот malloc@plt
```

Правильно — писать во временный файл **в том же каталоге**, ставить права/владельца
и делать `mv -f` (тот же fs = атомарно): старый inode доживает в уже отобразивших его
процессах, новый достаётся только тем, кто откроет путь после. `install.sh` в
`C:\Users\Nikita\unfuse-build\` переделан на это; штатный `module/customize.sh` беды
лишён — менеджер пишет в `modules_update` и переезжает на месте при перезагрузке.

## Состояние модуля — только в /data/adb/unfuse_zygisk.state (2026-10-07)

`preAppSpecialize` исполняется в домене **`zygote`** (до специализации), и политика
Zygisk Next даёт этому домену над `/data/adb` ровно `allow zygote adb_data_file dir
search` — этого хватает пройти по пути к собственному `.so` и **ни на что больше**.
`open(O_CREAT)` там падает, а отказ **заглушён `dontaudit`**: ни `avc:` в
`logcat -b all`, ни в `dmesg`. Отсюда «модуль молчит» — код был исправен всё время.

Ловится это только **поведением**: 4 секунды permissive (`setenforce 0` → запуск
свежего приложения → `setenforce 1` в том же скрипте) — в permissive маркер и сэмпл
появляются, обратно в enforcing пропадают. `dontaudit` глушит `avc` и в permissive,
так что avc-строки ждать бесполезно.

Решение: каталог `/data/adb/unfuse_zygisk.state/` с меткой
`u:object_r:magisk_file:s0` — тип, который политика отдаёт **всем** доменам
(`allow * magisk_file dir *`, `allow * magisk_file file *`), и файл внутри него
**наследует** метку (проверено: `touch` и `mkdir` внутри дали `magisk_file`). Своё
правило политики не нужно. Каталог создаёт и метит `post-fs-data.sh` при каждой
загрузке (`mkdir -p`, не `rm -rf` — `no_hooks` принадлежит пользователю).

Правило на будущее: **отказ не должен быть тихим.** В `claim_once` тихим остаётся
только `EEXIST` (маркер уже занят), всё остальное — громкая ошибка со
`strerror(errno)`. Выключатель `no_hooks` — **fail-open** осознанно: «каталог не
читается» не значит «пользователь хотел выключить», а тихое выключение превратило
бы сломанную установку в молчаливый no-op.

## Новая сборка `.so` не активна до перезагрузки (2026-10-07)

Zygisk Next открывает `module.so` **один раз при загрузке** (O_RDONLY,
`/proc/<zn-daemon>/fd/9`) и передаёт этот fd в zygote и в приложения — те `mmap`'ят
файл через fd демона, а не по пути. После `mv` путь ведёт на новый inode, а демон и
живые процессы держат старый (`… (deleted)` в `/proc/<pid>/maps`). Проверять:

```
stat -c '%i' /data/adb/modules/unfuse_zygisk/zygisk/arm64-v8a.so
ls -l /proc/$(pidof zn-daemon)/fd | grep unfuse
```

`cp -f` активировал сборку мгновенно — потому и ронял процессы. Так что атомарная
установка безопасна, но **инертна**: тестировать новую сборку только после
перезагрузки. Записано также в навыке `android-hot-swap-mapped-so-hazard`.

## Грабли устройства (кратко)

- `adb shell su -c '…;…'` ломается: adb рвёт по `;`, половина уходит от `shell`.
  Использовать `adb shell "su 0 sh /data/local/tmp/script.sh"`.
- `nsenter -t <pid> -m` запрещён под KernelSU. Пространство имён читается
  **резолвингом пути** через `/proc/<pid>/root/…` (stat/statfs), а не по таблице
  `/proc/<pid>/mounts`.
- toybox `stat` **не** разыменовывает последний симлинк, а `chown` — разыменовывает.
  `stat /sdcard` отдаёт владельца симлинка (`0:0`), а `chown … /sdcard` уходит по
  цепочке на сырое дерево и меняет владельца `/data/media/0` (должно оставаться
  `1023:1023`, mode `2770`). Записывать владельца для восстановления только после
  `readlink -f`.
- Арифметика шелла на устройстве 32-битная — смещения передавать десятичной строкой.
- `mountinfo` парсить по разделителю `-`, а не по номеру поля.
- IP устройства меняется после каждой перезагрузки; новый сообщает пользователь —
  не перезагружать без необходимости.
- `grep -i unmountable` ловит безобидное `requires state … unmountable` — исключать.
- **Для проверки снятия изоляции `Android/data` брать приложение БЕЗ «All files
  access».** У `com.termux` `MANAGE_EXTERNAL_STORAGE: allow`, то есть
  `mount_external` = `ANDROID_WRITABLE`, и Android сам может не ставить tmpfs — такой
  тест ничего не различает. Годится, например, `com.deepseek.chat` (`default`).
  Смотреть число записей в `/proc/<pid>/root/storage/emulated/0/Android/data` и
  fstype маунтов `Android/data` в `/proc/<pid>/mountinfo` (должны быть f2fs).
- `logcat -b all -d | grep avc` — единственный надёжный способ увидеть отказы
  SELinux; `dmesg` их почти не содержит, а `dontaudit` глушит совсем.
- `/data/tombstones/` нумеруется кольцом: свежие записи могут получить **меньший**
  номер, чем старые, — судить по mtime и по `Timestamp:` внутри файла.
- `ps -AZ` показывает домены: `zn-daemon` и companion'ы Zygisk Next живут в
  `u:r:ksu:s0`, сам zygote — в `u:r:zygote:s0`. Домен модуля в `preAppSpecialize`
  снаружи **не виден** (`/proc/<pid>` живого приложения показывает домен
  приложения); читается только изнутри — `/proc/self/attr/current`, и он теперь
  попадает в сэмпл.
- `su 0` на устройстве даёт домен `u:r:ksu:s0` — из него `mkdir` и `chcon` в
  `/data/adb` работают (в том числе `chcon u:object_r:magisk_file:s0`), а вот
