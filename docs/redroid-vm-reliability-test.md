# Тест надёжности unfuse_zygisk в redroid-ВМ (Android 11, SDK 30)

**Дата:** 2026-10-09, ~22:00–22:45
**Стенд:** контейнер `redroid11` (`redroid/magisk:11`) на телефоне `marble`,
доступ с ПК — `10.83.195.105:5556` (порт 5555 — сам телефон, не ВМ).
**Сборка модуля:** ветка `no-sdcardfs`, `zygisk/arm64-v8a.so` md5
`c05fdfc28649db4e2ed1673e2e05545f` (объявление `ZYGISK_API_VERSION 4`).
**Вопрос:** не происходит ли сбоев на FUSE при различных действиях.

## Короткий ответ

**Сбоев FUSE не обнаружено ни в одном из сценариев.** Ни одна операция не
завершилась ошибкой, и ни разу точка хранилища не откатилась с f2fs на FUSE.
Тип точки (`stat -f -c %t`) оставался `f2f52010` (f2fs) на протяжении всего
прогона — то есть bind `/data/media` всё время лежал поверх FUSE-тома, и FUSE
в пути данных не участвовал.

## Состояние модуля до тестов

| Проверка | Результат |
|---|---|
| `md5sum zygisk/arm64-v8a.so` | `c05fdfc2…` — сборка с правкой API 4 |
| `/cache/magisk.log` | `unfuse_zygisk: exec [post-fs-data.sh]`, `exec [service.sh]` — скрипты **выполняются** |
| `/data/adb/unfuse_zygisk.state/once` | создан — Zygisk-плечо загрузилось |
| `tools/vold-fusefs --check` | rc = 0 (патч vold на месте) |
| `tools/vold-noacl --check` | rc = 0 |

Попутно: в ВМ adb-shell по умолчанию `uid=2000`, root берётся `adb root`
(либо `su -c`). FUSE-слой обслуживает **FuseDaemon внутри
`com.android.providers.media.module`** (это дизайн A11) — отдельного процесса
`sdcard` тут нет, `pidof sdcard` пуст и это нормально.

## Методика

«Сбой на FUSE» фиксировался по трём независимым признакам:

1. **Тип точки.** После каждой группы операций — `stat -f -c %t` на
   `/storage/emulated/0` и `/mnt/user/0/emulated`. Ожидание: `f2f52010` (f2fs).
   Появление `65735546` (fuse) = bind пропал, приложение вернулось на FUSE.
2. **logcat** — поиск `Transport endpoint`, `ENOTCONN`, `Failed to start FUSE`.
3. **tombstones / ANR / FATAL** — падения процессов.

## Результаты по группам

### 1. Файловые операции (18 шагов) — FAIL = 0

mkdir -p (5 уровней) · write+read · append · rename · symlink · hardlink ·
chmod · truncate · пустой файл · rm · имя с пробелом и кириллицей · дерево
глубиной 25 · 1000 мелких файлов · перечитывание всех 1000 · 64 МиБ запись +
сверка md5 после `sync` · параллельная запись 4×8 МиБ · rename каталога с 1000
файлами · `rm -rf` всего дерева. **Все PASS, fs-тип всё время f2fs.**

### 2. Цикл тома `sm unmount/mount 'emulated;0'` — PASS

Это главная проверка: vold может перемонтировать том в любой момент.

| Момент | `/dev/fuse` маунтов | fs `/mnt/user/0/emulated` |
|---|---|---|
| до цикла | 4 | `f2f52010` (f2fs) |
| после `unmount` | 0 | `1021994` (том снят) |
| после `mount` | 4 | `f2f52010` — **bind восстановился сам** |

То же на трёх циклах подряд. Значит, патч `mount()` в vold действительно
накрывает FUSE-маунт bind'ом при каждом перемонтировании.

### 4. Перезагрузка гостя (`rd restart`) — PASS

После рестарта контейнера: `exec [post-fs-data.sh]` и `exec [service.sh]` снова
в логе, `state/once` пересоздан, `vold` получил новый pid (22), обе точки —
`f2f52010`. Повторные файловая батарея и цикл тома после ребута — снова FAIL = 0.

### 5. Отказ FUSE-демона — PASS (главный результат)

`kill -9` процессу `com.android.providers.media.module` (он и держит
`/dev/fuse`): FUSE-демон умер и перезапустился (pid 1181 → 3975), а
`/storage/emulated/0` **остался `f2f52010`**, чтение и запись продолжили
работать. То есть даже полный отказ FUSE не доходит до приложения — модуль
стоит выше него.

### 6. Выносливость — FAIL = 0

5 раундов × 300 файлов (создание → перечитывание → удаление): битых 0, fs-тип
после каждого раунда `f2f52010`.

## Ограничения этого прогона

- **dmesg в ВМ — это лог общего ядра телефона.** Контейнер делит ядро с
  `marble`, поэтому в dmesg видны `sdcardfs: removing <пакет>` от самого
  телефона. Считать FUSE-ошибки по dmesg тут нельзя — использовался logcat.
- **SELinux в ВМ выключен** (метки читаются как `HACKED`), поэтому отказы,
  связанные с политикой, здесь принципиально не наблюдаются. Это свойство
  стенда, а не модуля; на `marble` SELinux включён.
- Тесты шли от root, от `su 9997` и от одного запущенного приложения;
  сплошного перебора всех приложений не было.
- В ВМ лежит **устаревший `armeabi-v7a.so`** (md5 `5e5e15be…`, тогда как
  текущая сборка — `5dfc44ae…`). Для этой ВМ неважно (она 64-битная, Zygisk
  берёт `arm64-v8a.so`), но при следующей установке стоит обновить.

## Вывод

По совокупности: модуль в redroid-ВМ A11 работает **надёжно**. Ни один из
сценариев — включая перемонтирование тома, перезагрузку гостя и принудительную
смерть FUSE-демона — не привёл ни к ошибке операции, ни к откату на FUSE.
