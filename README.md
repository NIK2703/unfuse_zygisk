# sdcardfs Restore

Zygisk-модуль, возвращающий внутренней памяти поведение Android 10 и более
ранних версий: **прямой доступ ко всей памяти для всех приложений без
исключений**, без FUSE и без scoped storage.

Списка приложений нет и быть не должно — подмена выполняется для каждого
процесса, который запускает Zygote.

У модуля два пути к одной цели:

* **основной** — sdcardfs с маской `0007` и `gid=9997`;
* **альтернативный** — сырое дерево `/data/media` с POSIX ACL на ту же группу
  `9997`. Включается сам, когда в ядре нет `CONFIG_SDCARD_FS`.

Какой путь сработал, видно в логе: `sdcardfs подключён` либо
`сырой /data/media подключён`.

На альтернативном пути ACL приходится ещё и защищать от `vold`: он переписывает
`default`-ACL у `/data/media/<user>` своей записью для группы `1023` уже после
того, как отработают скрипты модуля. Гонку закрывает не повтор и не сторож, а
патч — в работающем `vold` обезвреживается `setxattr` (см. §3.3). Адрес берётся
из таблиц самого `vold`, поэтому патч не привязан к сборке.

* Устройство проверки: POCO F5 (marble), Android 16, ядро 5.10 с
  `CONFIG_SDCARD_FS`.
* Версия: **v3.1.0**

---

## 1. Что делает модуль

Ровно две вещи:

1. В `preAppSpecialize()` создаёт процессу приватный mount namespace и
   подкладывает под `/mnt/user/<user>/emulated` источник памяти. Дальше Zygote
   сам рекурсивно биндит `/mnt/user/<user>` на `/storage`, поэтому подмена
   оказывается и на `/storage/emulated`.
2. Сбрасывает `*args->mount_storage_dirs` в `false`. Штатно Zygote накрывает
   `/storage/emulated/<user>/Android/{data,obb}` временным tmpfs и биндит туда
   каталоги **только своего пакета**; флаг отключает эту изоляцию, и
   `Android/data` с `Android/obb` отдаются целиком.

Всё остальное — вспомогательные скрипты, без которых эти две вещи не заработают
(см. §3).

## 2. Механика

```
preAppSpecialize(args)
  ├─ mount_external ∈ {DEFAULT, ANDROID_WRITABLE}?   иначе выход
  ├─ unshare(CLONE_NEWNS)
  ├─ mount(NULL, "/", MS_REC|MS_PRIVATE)
  ├─ attach("/mnt/user/<user>/emulated")
  │    ├─ bind /mnt/runtime/full/emulated  -> statfs == 0x5dca2df5 ?
  │    │     да  -> основной путь
  │    │     нет -> umount2(MNT_DETACH) и дальше
  │    └─ bind /data/media                 -> statfs == 0x65735546 (FUSE) ?
  │          нет -> альтернативный путь;  да -> откат, процесс без подмены
  ├─ (ANDROID_WRITABLE) то же для /mnt/androidwritable/<user>/emulated
  └─ *args->mount_storage_dirs = JNI_FALSE
```

Источник выбирается **по факту, а не по конфигу**: проверяется не успех
`mount(2)`, а тип ФС, реально оказавшейся под точкой (`statfs`). Без sdcardfs в
ядре `storage.sh` смонтировать его не может, и bind подсунул бы пустой каталог —
`statfs` это ловит, маунт откатывается и берётся сырое дерево. Такой же откат
страхует от того, чтобы приложение осталось вообще без памяти.

Обрабатываются два режима внешнего хранилища:

| режим | кто | обрабатывается |
|---|---|---|
| `DEFAULT` (1) | все обычные приложения | да |
| `ANDROID_WRITABLE` (4) | приложения с `MANAGE_EXTERNAL_STORAGE` и провайдер SAF `com.android.externalstorage`, через который ходит системное приложение «Файлы» | да |
| `NONE` (0) | изолированные процессы — внешнего хранилища у них нет вовсе | нет |
| `INSTALLER` (2) | `installd` | нет |
| `PASS_THROUGH` (3) | MediaProvider — ему нужен сырой `/data/media` | нет |

Последним трём подмена сломала бы сам слой хранилища.

## 3. Почему нужны скрипты

Модуль умеет только подкладывать готовый источник. Поэтому к моменту старта
первого приложения уже должны существовать:

* ярлык `media_rw_data_file` на корне `/data/media`;
* маунты `/mnt/runtime/*/emulated` — для основного пути;
* ACL на дереве `/data/media` — для альтернативного.

Всем этим занимается `module/storage.sh`, который вызывают `post-fs-data.sh` (до
Zygote) и `service.sh` (повторно, после vold). Шаги идемпотентны. Там же, на
альтернативном пути, `post-fs-data.sh` и `service.sh` ставят патч `vold` — без
него vold перепишет `default`-ACL у `/data/media/<user>` уже после скриптов
(см. §3.3).

### 3.1. Маунты `/mnt/runtime/*/emulated`

На этой прошивке `external_storage.sdcardfs.enabled=0` (задано в
`/vendor/build.prop`), поэтому vold **не** выполняет `/system/bin/sdcard` и
`/mnt/runtime/*/emulated` остаются пустыми каталогами. Модулю нечего
подкладывать — маунты создаёт `storage.sh`.

**Почему не `/system/bin/sdcard`.** AOSP-овский `sdcard.cpp` создаёт реальным
`mount(2)` только `/mnt/runtime/default/emulated`, а `read`/`write`/`full` — через
`sdcardfs_setup_bind_remount()`, то есть bind + `MS_REMOUNT` с новыми
`mask=`/`gid=`. В этом ядре `sdcardfs_remount_fs()` опции не разбирает
(заглушка), а vfsopts живут в superblock, поэтому все четыре маунта получают
опции `default` (`gid=1015`, `mask=6`) и становятся бесполезны для приложений.
Каждый маунт создаётся отдельным `mount(2)` — тогда у каждого свой анонимный
superblock и свои vfsopts.

Опции повторяют `system/core/sdcard/sdcard.cpp` (`mask` печатается в десятичном
виде — там `StringPrintf("mask=%d", mask)` над octal-литералом):

| точка | `mask` | `gid` |
|---|---|---|
| `default` | `6` (oct 0006) | `1015` AID_SDCARD_RW |
| `read` | `23` (oct 0027) | `9997` AID_EVERYBODY |
| `write` | `7` (oct 0007) | `9997` |
| `full` | `7` (oct 0007) | `9997` |

Модуль берёт именно `full`: драйвер считает права как `0775 & ~mask`, поэтому
каталоги получаются `0770`, файлы `0660`, а `AID_EVERYBODY` есть у любого
процесса. Итог — полный доступ ко всей памяти, включая `Android/data`,
`Android/obb` и каталоги чужих пакетов. Ровно так же вёл себя маунт `full` на
Android 9 и раньше.

### 3.2. Ярлык корня `/data/media`

sdcardfs своих данных не хранит: он пробрасывает операции к нижнему слою
(`/data/media`) и не заводит отдельного инода для корня точки монтирования —
`getattr()` корня форвардится в нижний инод. У этого корня ярлык особый:

```
private/file_contexts:633   /data/media     u:object_r:media_userdir_file:s0
private/file_contexts:634   /data/media/.*  u:object_r:media_rw_data_file:s0
private/domain.te:252       allow { coredomain appdomain } media_userdir_file:dir search;
```

для `media_userdir_file` разрешён ровно один `search`, без `getattr`:

```
stat /storage/emulated    -> Permission denied   (и без единого AVC: dontaudit)
stat /storage/emulated/0  -> ok
```

Содержимое работает и так: там ярлык `media_rw_data_file`, на который у
appdomain полные права (`app.te:149`). А вот сам корень — нет, и это ровно то
ограничение доступа, которого быть не должно.

`storage.sh` возвращает корню ярлык `media_rw_data_file` — тот же, что был у
`/data/media` на Android 10 и раньше (тогда отдельного типа
`media_userdir_file` просто не существовало).

Патчить sepolicy не нужно: право уже есть, а `relabelto` для домена zygote
запрещён neverallow (`domain.te:791`) — поэтому перемаркировка делается
скриптом, а не из процесса приложения.

На альтернативном пути перемаркировка ещё и обязательна: под `/storage/emulated`
ложится само дерево `/data/media`, и без `media_rw_data_file` на его корне
appdomain не получит даже `search`.

### 3.3. Альтернативный путь: ACL на сыром дереве

Когда sdcardfs в ядре нет, под `/mnt/user/<user>/emulated` ложится само
`/data/media`. Это не изобретение модуля: **ровно то же делает AOSP** на
платформе без sdcardfs — `vold-16/Utils.cpp:1691` биндит туда
`absolute_lower_path`, то есть сырое дерево, и отдаёт получившийся
`/mnt/pass_through/<user>/emulated` привилегированным потребителям. Модуль
просто отдаёт этот вид всем приложениям.

Проблема в правах: дерево принадлежит `1023:1023` (`media_rw`) с режимами
`0550` на корне, `2770` на `/data/media/0` и `0670` на файлах, а в группах
приложений `1023` нет. Без правки приложение не войдёт даже в корень.
sdcardfs эту работу делает сам, отдавая каталоги `0770` и файлы `0660` для
`gid 9997`; на альтернативном пути то же самое выставляется POSIX ACL.

**Почему именно 9997.** `AID_EVERYBODY` — «shared between all apps in the same
profile» (`system-core-16/.../android_filesystem_config.h:166`), и это ровно тот
gid, с которым смонтированы sdcardfs-маунты `read`/`write`/`full`
(`system-core-16/sdcard/sdcard.cpp:182`). Доступ получают все приложения, а не
список избранных. Проверено на устройстве: 9997 есть у 78 процессов из 80;
исключения — `99000`/`99001` (`ISOLATED_APP_UID_BASE`), и они же лишены прав на
`media_rw_data_file` в `app.te`.

**Почему ACL, а не chmod.** Две причины:

* `vold` при каждой загрузке пересобирает `/data/media`, `Android`,
  `Android/data`, `Android/obb` и `Android/media` через `fs_prepare_dir()`
  (`chown` + `chmod`). `chmod` правит в ACL только `USER_OBJ`/`GROUP_OBJ`/`MASK`/
  `OTHER` и **не трогает именованные записи** — выданный доступ это переживает.
  Проверено: ACL, расставленные до перезагрузки, остались на месте после неё.
* `umask` приложений — `0077`, он бы обнулял групповые биты у всего, что они
  создают. Но если у каталога есть **default ACL**, ядро вообще не применяет
  umask: `vfs_create()` пропускает `mode &= ~current_umask()`, а
  `posix_acl_create()` считает режим пересечением с ACL
  (`fs/posix_acl.c`, Linux 5.10). Поэтому `storage-fix` пишет и access-, и
  default-ACL: файл, созданный приложением с `0666` и `umask 077`, выходит
  `0660` с унаследованной записью для 9997 — и его сразу видят все приложения.

Утилита `module/tools/storage-fix` (исходник — `tools/storage-fix.c`) строит ACL
ровно по образцу `vold::SetDefaultAcl` (`vold-16/Utils.cpp:142`), но с именованной
записью для 9997:

```
USER_OBJ  <- владелец
GROUP_OBJ <- группа
GROUP     <- 9997        <- то, чего нет у vold
MASK      <- группа      <- без него именованная запись обнулилась бы
OTHER     <- 0           <- см. ниже
```

Режимы: каталоги — владелец + `rwx` группе; файлы — владелец + `rw` группе (плюс
сохранённый `x`); корню тома (`--traverse`) — только `r-x`, его нужно пройти,
писать в него нечего. Проход по дереву `/data/media/0` (1188 каталогов, ~7000
файлов) занимает около секунды.

**`OTHER` обнуляется — и это не мелочь.** Доступ выдаёт именованная запись для
9997, а не бит «остальных». Если оставить его таким, каким он был на диске,
объекты, поправленные на загрузке, и объекты, созданные приложением (их режим
считает хук libc, а ACL он пишет с `OTHER=0`), выглядели бы по-разному — и
«остальные» получили бы доступ **в обход** записи для 9997, то есть шире, чем на
Android 10, где sdcardfs пускал только процессы из группы 9997. Заодно это
приводит альтернативный путь к тому же виду, что и основной: маунт `full` с
`mask=0007` и `gid=9997` даёт каталоги `0770` и файлы `0660` (`0777 & ~7` и
`0666 & ~7`), а «остальные» там нулевые по построению.

**Гонка с vold.** vold готовит `/data/media` не один раз, и не всегда до того,
как отработают скрипты модуля. Все три места, где он пишет **default**-ACL, лежат
на альтернативном пути:

| что | где | что попадает в ACL |
|---|---|---|
| `/data/media/<user>` | `FsCrypt.cpp:1027` | именованная запись для **1023** |
| `/data/media/<user>/Android/obb` | `Utils.cpp:1889` | именованной записи нет вовсе |
| `/data/media/<user>/Android/{data,obb,media}/<pkg>` | `Utils.cpp:406` | запись для uid пакета |

`vold::SetDefaultAcl` (`Utils.cpp:142`) собирает ACL с нуля и зовёт
`setxattr(system.posix_acl_default, ...)` — то есть **заменяет** её целиком,
вместе с нашей записью для 9997. Разница с `chmod` здесь принципиальна: `chmod`
правит только `USER_OBJ`/`GROUP_OBJ`/`MASK`/`OTHER` и именованных записей не
трогает, поэтому `fs_prepare_dir()` вреда не наносит, а `SetDefaultAcl` —
наносит.

Чем это плохо: каталог, созданный в таком месте процессом, на который хуки libc
не распространяются (vold, MTP, root-демон), наследует default-ACL родителя —
чужую запись вместо 9997 — и приложения его не видят. Доступ выдаёт именно
именованная запись, а не режим.

Момент последней правки заранее неизвестен и таймером не ловится: `/data/media/0`
vold правит при подготовке CE-хранилища пользователя (на стадии `post-fs-data` он
делает только DE — `FsCrypt.cpp:657`), а каталоги пакетов — вообще когда угодно,
вплоть до установки приложения через час после загрузки.

**Поэтому модуль обезвреживает не ACL, а сам vold.** Гоняться за vold повторами
бессмысленно — момент правки заранее неизвестен, — а держать сторож значит всегда
иметь на устройстве лишний долгоживущий процесс. Вместо этого в работающем `vold`
заменяется на пустышку единственная функция, которая пишет `default`-ACL, —
`setxattr(2)`.

Почему именно `setxattr` — это следует из таблиц самого бинарника, а не из
чтения исходников:

* во всём `vold-16` `setxattr` вызывается **ровно один раз** (`Utils.cpp:195`,
  внутри `vold::SetDefaultAcl`), а `getxattr` не вызывается **нигде**. Значит,
  обезвредить `setxattr` — то же самое, что обезвредить `SetDefaultAcl`, и
  никаких других последствий у этого нет;
* `SetDefaultAcl` — единственный источник `default`-ACL: все три места из
  таблицы выше приходят именно в него. Одним патчем закрываются все три;
* `lsetfilecon` из `vold_prepare_subdirs.cpp:100` живёт в отдельном бинарнике
  (`vold_prepare_subdirs`) и `default`-ACL не пишет вовсе — его трогать не надо.

Замена — две инструкции вместо первой: `mov w0, #0` и `ret`. Восемь байт, одна
запись `pwrite(2)`; разорванного состояния не бывает. Возвращается именно `0`
(`android::OK`), потому что вызывающий проверяет результат:
`FsCrypt.cpp:1028` — `if (ret != android::OK) return false;`. Ответь патч `-1`,
подготовка хранилища пользователя сорвалась бы.

**Как находится адрес — без привязки к сборке.** `setxattr` для `vold` —
импортируемый символ libc, и это даёт адрес по имени, а не по байтовой подписи:

1. в `.dynsym` ищется символ `setxattr`; в `.rela.plt` ему соответствует
   `R_AARCH64_JUMP_SLOT`, откуда берётся слот GOT;
2. слот GOT — это то, что читает `ldr` внутри трамплина `.plt`. Утилита
   **декодирует** трамплины и ищет тот, чей `ldr` читает именно этот слот, — то
   есть найденное место подтверждает себя само, а не сверяется с записанной
   заранее подписью.

Имя символа не меняется ни при обновлении прошивки, ни при смене версии `vold`,
поэтому патч переживает и то, и другое. Единственное, что нужно знать о раскладке
`.plt`, — постоянную `C` в `адрес_трамплина = C + 16 * номер_релокации`. Она не
берётся на веру: утилита выводит её из **других** символов, которые ещё не
пропатчены. Это же делает возможным повторный запуск — после патча `ldr` у
`setxattr` уже нет, и найти его трамплин декодированием нельзя; он находится по
выведенной `C` и проверяется по остатку (`add`/`br`). Отсюда `--check` и
идемпотентность: второй запуск видит, что патч на месте, и ничего не пишет.

Патч ставится в `post-fs-data.sh` и повторно в `service.sh`. Второй проход — не
«на всякий случай»: он подтверждает, что патч встал, и попадает в журнал строкой
`патч vold на месте — vold не пишет default-ACL`. На этой прошивке `vold` уже
работает к моменту `post-fs-data`, так что патч встаёт на самой ранней стадии —
задолго до того, как `system_server` попросит `vold` подготовить CE-хранилище
пользователя (`fscrypt_prepare_user_storage()`, откуда и приходит правка).

**Замерено A/B на двух загрузках одного и того же устройства** (POCO F5,
Android 16, принудительный альтернативный путь; в обоих случаях патчер выключен и
включён в активном каталоге модуля, разница только в этом):

| | патчер выключен | патчер включён |
|---|---|---|
| `default GROUP` у `/data/media/0` | `id=1023` | `id=9997` |
| каталог, созданный под ним | `id=1023` | `id=9997` |
| файл, созданный в этом каталоге | `id=1023` | `id=9997` |

В контрольной загрузке `storage-fix` на стадии `service` записал 9997 в обе ACL и
отчитался об этом в журнале — и всё равно к концу загрузки в `default`-ACL стояла
запись vold для 1023. С патчем она не появляется, и всё, что создаётся после,
наследует 9997.

**Как определяется, что путь нужен.** Основной путь считается поднятым, только
если под всеми четырьмя точками `/mnt/runtime/*/emulated` действительно
sdcardfs. Тип берётся из **последней** записи `/proc/mounts` для этого пути:
маунты идут в порядке наложения, поэтому последняя — верхняя, а наивный `grep`
видит и то, что лежит под точкой, и ошибается.

Читается `/proc/mounts` **только средствами шелла**, без `stat(1)`. Это не
придирчивость: на стадиях модуля KernelSU подставляет свой busybox, и его
`stat -f -c %T` печатает `UNKNOWN` вместо магического числа — проверка молча
ломается. Замерено на устройстве в одном и том же окружении:

| | post-fs-data | service |
|---|---|---|
| `stat -f -c %T` (busybox) | каталогов ещё нет | `UNKNOWN` |
| чтение `/proc/mounts` шеллом | пусто | `sdcardfs` |

## 4. Требования

1. Zygisk: Magisk или ZygiskNext (KernelSU/APatch).
2. Android 11+ (проверено на Android 16).
3. Ядро с `CONFIG_SDCARD_FS` — **желательно, но не обязательно**. Без него
   модуль уходит на альтернативный путь; ему нужны `CONFIG_F2FS_FS_POSIX_ACL`
   и `acl` в опциях монтирования `/data` (на современных ядрах так и есть).

## 5. Сборка и установка

### 6.1. Принудительный альтернативный путь (временно, для тестов)

На ядре с `CONFIG_SDCARD_FS` альтернативный путь сам не включается — он
предназначен для ядер без sdcardfs. Чтобы прогнать его на обычном ядре, есть
переключатель: если существует файл `/data/adb/sdcardfs_restore.force_raw`,
`storage.sh` не поднимает sdcardfs и снимает прежние маунты, после чего модуль
уходит на сырое дерево.

```sh
# включить
adb shell su -c 'touch /data/adb/sdcardfs_restore.force_raw'
adb shell su -c 'sh /data/adb/modules/sdcardfs_restore/storage.sh test'
adb shell am force-stop com.termux          # приложение перезапустится через модуль

# выключить
adb shell su -c 'rm /data/adb/sdcardfs_restore.force_raw'
adb reboot
```

Признак того, что включился именно он: в `/data/adb/sdcardfs_restore.log`
появляется `ТЕСТ: ... основной путь выключен принудительно`, затем
`альтернативный путь: ACL с группой 9997 расставлены`, а в logcat —
`сырой /data/media подключён`. Под `/storage/emulated/0` при этом лежит `f2fs`
(сырое дерево), а не `sdcardfs`.

### 6.2. Проверка хука libc (альтернативный путь)

На альтернативном пути модуль правит входы libc в процессе приложения, чтобы
режимы и ACL создаваемых файлов совпадали с тем, что отдавал sdcardfs. Проверять
это нужно на **настоящей** libc с устройства, а не на хостовой: и цели патча, и их
размеры зависят от конкретной сборки bionic. Поэтому обе проверки работают с
копиями, снятыми с устройства.

```sh
adb pull /apex/com.android.runtime/lib64/bionic/libc.so device/libc/libc-arm64.so
adb pull /apex/com.android.runtime/lib/libc.so        device/libc/libc-arm.so

# 1. Предварительная проверка на хосте: безопасен ли патч для каждой цели
python3 tools/verify-hook-targets.py device/libc/libc-arm64.so
```

Проверка разбирает ELF сама (заголовок, секции, `.dynsym`, `.rela.plt`), считает
размер каждой цели, разматывает цепочки переходников до корня через таблицу
релокаций, проверяет выравнивание и наложения патчей, а затем **пишет патч в
копию файла и дизассемблирует её** — то есть доказывает, что 16 байт кодируются
именно так, как ожидается. Итог на libc-16:

```
итог: ok=22  пропущено=0  нельзя=0
корней патчится: 9 — __open_2, __openat_2, fchmod, fchmodat, linkat, mkdirat,
                       open, openat, renameat2
```

Девять корней — ровно те, что патчит движок на устройстве; остальные тринадцать
покрыты через них. Код возврата 1, если хоть одна цель небезопасна или не
покрыта.

```sh
# 2. Самопроверка на устройстве — 28 проверок
sh tools/build-hookselftest.sh
adb push out/hookselftest-arm64 /data/local/tmp/hookselftest
adb shell su -c '/data/local/tmp/hookselftest'

# 3. Сквозная проверка из namespace НАСТОЯЩЕГО приложения
adb push tools/device-e2e.sh /data/local/tmp/
adb shell su -c 'sh /data/local/tmp/device-e2e.sh'
```

Сквозная проверка берёт живой процесс приложения, заходит в его mount namespace и
сравнивает вид хранилища с корневым:

```
--- корневой namespace (ожидается FUSE) ---
/storage/emulated/0   0x65735546  FUSE    dev=127
--- namespace приложения (ожидается f2fs — сырое дерево) ---
/storage/emulated/0   0xf2f52010  f2fs    dev=66321
/data/media/0         0xf2f52010  f2fs    dev=66321
```

Затем она создаёт файл от uid приложения с режимом `0600`, убеждается, что вышел
`0660` с записью ACL для 9997, и что этот файл открывает **другой** uid.

**Осторожно с `Bad address`.** Если открывать файл на `/storage/emulated/0` от
чужого uid в **корневом** namespace, `open()` возвращает `EFAULT`. Это свойство
самого FUSE-монтирования, а не модуля: демон MediaProvider не обслуживает uid, не
принадлежащие этому пространству имён, и то же самое воспроизводится на файле,
которого модуль никогда не касался. Поэтому проверка «видит ли файл другое
приложение» обязана выполняться **внутри** namespace приложения: там под
`/storage/emulated/0` лежит сырое дерево, и тот же uid читает чужой файл без
всяких препятствий. Ради этого модуль и существует.

### 6.3. Патч vold

Патч ставится сам — в `post-fs-data.sh` и `service.sh`, — и на обеих стадиях
идемпотентен: если он уже стоит, утилита это видит и ничего не пишет. Руками его
нужно трогать только для проверки.

```sh
M=/data/adb/modules/sdcardfs_restore

# состояние: 0 — патч на месте, 1 — трамплин цел (патча нет),
# 2 — не удалось разобрать vold, 3 — не удалось записать
adb shell su -c "$M/tools/vold-noacl --check"; echo "код $?"

# найти и показать адреса, ничего не писать
adb shell su -c "$M/tools/vold-noacl --dry-run"

# поставить патч (повторный запуск — no-op)
adb shell su -c "$M/tools/vold-noacl"
```

Что печатает разбор (живой `vold`, POCO F5, Android 16):

```
vold-noacl: vold pid=899 база=0x5a1b01f000; setxattr -> .rela.plt[185],
            GOT 0x1002b8, трамплин 0xfa5d0 (в процессе 0x5a1b1195d0),
            сдвиг раскладки 63908, вызовов 1
vold-noacl: патч поставлен: setxattr в vold больше не пишет default-ACL
            (mov w0, #0; ret по 0x5a1b1195d0)
```

Обратите внимание на пару чисел. **База загрузки каждый раз разная** — её выбирает
ASLR (`0x5a1b01f000` на этой загрузке, `0x5c14042000` на предыдущей), поэтому
адрес в процессе всегда новый. А **`трамплин 0xfa5d0` и `сдвиг раскладки 63908`
одни и те же во всех загрузках**: это смещения внутри файла `/system/bin/vold`, и
берутся они из его таблиц, а не из памяти процесса.

**Проверка на хосте, без устройства.** Утилите можно дать сам файл `vold`
(`--file`) — она разберёт его так же, как живой процесс, и ничего не запишет. Это
годится, чтобы проверить патч против чужой сборки до прошивки:

```sh
adb pull /system/bin/vold /tmp/vold                 # или взять из образа
clang -std=c11 -O2 -Wall -Wextra -o /tmp/vold-noacl tools/vold-noacl.c

/tmp/vold-noacl --file /tmp/vold --check     # 0 — патч есть, 1 — нет
/tmp/vold-noacl --file /tmp/vold --dry-run   # адреса, без записи
/tmp/vold-noacl --file /tmp/vold --selftest  # сопоставление релокаций и трамплинов
```

`--selftest` проверяет саму раскладку, а не патч: он требует, чтобы **каждой**
релокации `JUMP_SLOT` нашёлся ровно один трамплин и чтобы разным символам
достались разные трамплины. На настоящем `vold` (POCO F5, Android 16):

```
JUMP_SLOT 473, сопоставлено 473, без трамплина 0, неоднозначных 0,
не JUMP_SLOT 0, повторов 0, трамплинов всего 473 (пропатчено 0)
сопоставление взаимно однозначное
```

473 на 473 без единого пропуска и повтора — значит «релокация → трамплин»
разрешается однозначно, и адресной арифметики вида `plt + 16 * (i + 1)` не
требуется. На **уже пропатченном** образе полной биекции быть не может: у
пропатченного трамплина нет `ldr`. Такой образ даёт `473 JUMP_SLOT, сопоставлено
472, без трамплина 1, пропатчено 1` и вердикт `сопоставление взаимно однозначное
(кроме пропатченных)` — пропуск засчитывается, только если он объясняется нашим
же патчем, иначе это была бы настоящая дыра, замаскированная под патч. Приготовить
такой образ, не трогая устройство:

```sh
python3 tools/elf-fake-patch.py /tmp/vold /tmp/vold.patched 0xfa5d0
/tmp/vold-noacl --file /tmp/vold.patched --check     # код 0
```

**A/B: как убедиться, что патч действительно закрывает гонку.** Проверка ставится
на двух загрузках, и разница между ними ровно одна: есть ли в активном каталоге
модуля файл `tools/vold-noacl`.

```sh
# контрольная загрузка: убрать патчер и перезагрузиться
adb shell su -c "mv $M/tools/vold-noacl $M/tools/vold-noacl.off"
adb reboot

# ...после загрузки
adb shell su -c '/data/local/tmp/acl-dump /data/media/0'
#   access  GROUP rwx id=9997     <- проход модуля отработал
#   default GROUP rwx id=1023     <- vold переписал ПОСЛЕ него
```

Дальше `vold-noacl.off` возвращается на место, загрузка повторяется — и в
`default`-ACL остаётся `id=9997`. Готовые скрипты для обеих загрузок:
`tools/ab-probe.sh` (снимает показания) и `tools/storage-map.sh` (показывает, какой
путь задействован и лежат ли на месте маунты sdcardfs).

Почему контрольная загрузка вообще ломается, видно по её же журналу: `storage-fix`
на стадии `service` записал 9997 в **обе** ACL и отчитался
`ACL /data/media/0: запись 9997 на месте в обеих ACL` — и всё равно к концу
загрузки в `default`-ACL стояла запись vold для 1023. Это и есть гонка, которую
закрывает патч.

Что ещё стоит посмотреть руками:

```sh
# что именно лежит в ACL (штатный getfattr не годится: toybox-овский обрывает
# значение на первом NUL, то есть на поле версии)
clang -std=c11 -Oz tools/acl-dump.c -o /tmp/acl-dump
adb push /tmp/acl-dump /data/local/tmp/acl-dump
adb shell su -c '/data/local/tmp/acl-dump /data/media/0'
#   /data/media/0 access  GROUP     rwx id=9997
#   /data/media/0 default GROUP     rwx id=9997

# инвариант альтернативного пути — код 0/1, годится и для скриптов
adb shell su -c "$M/tools/storage-fix --check /data/media/0"
#   ОК   /data/media/0  access=rwx default=rwx
```

`tools/acl-break` — стенд, который пишет `default`-ACL ровно так, как это делает
`vold::SetDefaultAcl` (`USER_OBJ=7 GROUP_OBJ=7 GROUP(1023)=7 MASK=7 OTHER=0`), и в
модуль не входит. Он нужен, чтобы воспроизвести контрольную половину A/B на живой
загрузке, не перезагружаясь.

**Чего патч не делает.** Он живёт в памяти процесса, а не на диске: `/system/bin/vold`
не меняется, и после перезагрузки патч ставится заново. Если `vold` когда-нибудь
будет перезапущен посреди работы (это аварийный сценарий, а не штатный), патч
вместе с процессом пропадёт до следующей загрузки — см. §7.

## 7. Ограничения

* Обрабатываются только процессы, которые запускает Zygote. Процессы, читающие
  сырой `/data/media` (MediaProvider, `installd`), намеренно не трогаются.
* Поддержка только внутреннего хранилища; adoptable storage не обрабатывается.
* Многопользовательский режим поддержан (`user_id` берётся из `uid`), но
  проверялся только на user 0.
* На альтернативном пути нет виртуализации `fsuid`/`fsgid`, какую даёт sdcardfs:
  приложение, которое сделает `chown` своему `Android/data/<pkg>`, сломает доступ
  к этому каталогу для MediaProvider. Это свойство любого решения без sdcardfs,
  включая AOSP-овский `/mnt/pass_through`.
* Патч `vold` живёт **в памяти процесса**, а не на диске: `/system/bin/vold` не
  меняется, и после каждой загрузки патч ставится заново. Если `vold` окажется
  перезапущен посреди работы (аварийный сценарий, не штатный), патч пропадёт
  вместе с процессом, и `default`-ACL у `/data/media/0` снова получит запись для
  1023 — до следующей загрузки. Штатной эта ситуация не является: `vold` —
  долгоживущий процесс, а патч ставится на самой ранней стадии, когда он уже
  поднят.
* Патч рассчитан на AArch64. На 32-битном `vold` утилита честно откажется (код 2)
  вместо того, чтобы писать наугад: раскладка `.plt` там другая, и её проверка не
  проводилась. Устройства, где `vold` 32-битный, останутся без патча.
* Патч обезвреживает `setxattr` в `vold` **целиком**, а не только вызов из
  `SetDefaultAcl`. Сегодня это одно и то же (в `vold-16` других вызовов нет, и
  `getxattr` не вызывается вовсе), но если вендор добавит в `vold` свой
  `setxattr` для чего-то другого, он тоже перестанет работать. Проверяется одной
  командой: `vold-noacl --dry-run` печатает `вызовов N` — там должно быть `1`.
* Многопользовательский режим: сплошной рекурсивный проход `storage-fix` делает
  только по `/data/media/0`, у остальных пользователей дерево правится при
  первом обращении. Проверялось только на user 0.

## 9. История версий

* **v3.1.0** — сторож убран, вместо него снова патч `vold`, но уже без привязки к
  сборке. Это ответ на слабое место v3.0.0: сторож держал инвариант и не смотрел в
  код `vold`, однако сам был лишним долгоживущим процессом на устройстве, а
  гонку он не предотвращал, а догонял — правка возвращалась уже после того, как
  vold успевал переписать `default`-ACL. Патч же не даёт записи случиться вовсе.
  Отличие от v2.9.0 принципиальное: там адрес искался по байтовой подписи
  конкретной сборки, а здесь — по таблицам самого `vold` (`.dynsym` → `.rela.plt`
  → слот GOT → декодированный трамплин `.plt`), поэтому обновление прошивки его не
  ломает. Проверено A/B на двух загрузках: без патчера `default`-ACL у
  `/data/media/0` = `GROUP(1023)` и наследуется вниз по дереву, с патчером =
  `GROUP(9997)`. Утилита `vold-noacl` переписана (1255 строк вместо 495), у неё
  появились `--selftest` (проверка раскладки `.plt`: 473 релокации ↔ 473
  трамплина, без пропусков и повторов), осмысленный `--check` в режиме `--file`
  и `--dry-run`. Из `storage-fix` вырезан весь режим сторожа (`--guard`, `inotify`,
  `flock`), из `service.sh` — таймерные проходы; `storage.sh` вместо запуска
  сторожа пишет в журнал отчёт о состоянии ACL. Заодно исправлено: `warn()` писал
  префикс в `stderr`, а текст через `vprintf` в `stdout`, из-за чего при `2>&1`
  строки в журнале расходились.
* **v3.0.0** — патч `vold` убран целиком, вместо него сторож ACL. Патч заменял в
  памяти `vold` одну инструкцию в `vold::SetDefaultAcl()` и был привязан к
  конкретной сборке `/system/bin/vold`: после обновления прошивки он перестал бы
  находить сигнатуру, а вместе с ним вернулась бы и гонка. Сторож
  (`storage-fix --guard`) держит не адрес инструкции, а инвариант — запись 9997 в
  ACL, — и возвращает её по событию `inotify`: `setxattr` меняет метаданные inode
  и приходит как `IN_ATTRIB`. Ничего зависящего от сборки в нём нет, поэтому он
  переживает и обновление прошивки, и смену версии `vold`. Заодно ушли три
  таймерных прохода ACL и весь код патчера (`tools/vold-noacl.c`, 495 строк);
  вместо него `--check` (проверка инварианта, код 0/1) и `--guard` (сторож).
  Логика сторожа проверена на хосте (`tools/test-guard-host.sh`, 8 проверок) и на
  устройстве (`tools/test-guard.sh`).
  **Отменено в v3.1.0** — сторож не предотвращал гонку, а догонял её, и был лишним
  процессом; патч v3.1.0 закрывает ту же гонку, не будучи привязанным к сборке.
* **v2.9.0** — гонка с vold за `default`-ACL у `/data/media/0` устранена, а не
  замаскирована повторами. Новая утилита `tools/vold-noacl` заменяет в памяти
  `vold` одну инструкцию в `vold::SetDefaultAcl()`: функция сразу возвращает `OK`
  и не пишет default-ACL вообще — ровно так, как она ведёт себя на устройствах с
  sdcardfs. Так закрываются сразу все три её вызова (`/data/media/<user>`,
  `Android/data/<pkg>`, `Android/obb`). Пишется через `/proc/<pid>/mem`, без
  `PTRACE_ATTACH`, — процесс не останавливается, заморозить vold нечем; перед
  записью утилита сверяет найденное место с ожидаемым и при чужой сборке `vold`
  молча отказывается (код 2). Патч ставится в `post-fs-data.sh` (vold готовит
  CE-хранилище пользователя только позже) и повторно в `service.sh`. Три
  таймерных прохода ACL стали запасным путём и выполняются только если патч не
  встал. Проверено A/B на одном пути загрузки при отключённых повторах: без
  патча `default`-ACL = `GROUP(1023)`, с патчем = `GROUP(9997)`.
  **Отменено в v3.0.0** (тот же A/B-результат даёт сторож, не заглядывая в код
  `vold` вообще) и **возвращено в v3.1.0** в том же виде, но без привязки к
  сборке: адрес берётся из таблиц `vold`, а не из байтовой подписи.
* **v2.8.0** — закрыты две дыры в правах на альтернативном пути, обе найдены на
  устройстве:
  * `storage-fix` больше не переносит в ACL бит «остальных» с диска: он
    обнуляется, как это делает хук libc. Иначе объекты, поправленные на загрузке,
    и объекты, созданные приложением, выглядели бы по-разному, а «остальные»
    получали бы доступ в обход именованной записи для 9997 (замерено: файл `0664`
    получал `OTHER=4`). Заодно альтернативный путь приведён к тому же виду, что и
    основной: каталоги `0770`, файлы `0660`.
  * `service.sh` после `sys.boot_completed` делает ещё три прохода ACL (паузы 15,
    30 и 75 секунд) — vold дописывает `/data/media/0` default-ACL с записью для
    1023 **после** скриптов модуля, и наследование в этот каталог ломалось.
    Проходы идут фоном, `service.sh` возвращается сразу.
* **v2.7.0** — правка входов libc на альтернативном пути (`src/hook_libc.cpp`).
  Приложение, создающее файл с узким режимом, получало файл, невидимый другим:
  на сыром дереве нет sdcardfs, который привёл бы режим и ACL к общему виду.
  Теперь входы `open`/`openat`/`mkdirat`/`fchmodat`/`renameat2`/`linkat` и
  покрытых через них функций заменяются переходом на обработчик, который считает
  режим как sdcardfs и дописывает ACL с записью для 9997. Патч решается по
  размеру функции (не короче 16 байт), размеры читаются из `.dynsym` на диске —
  на libc-16 из 22 целей патчатся 9 корней, остальные 13 покрыты через `.plt`.
  Добавлены `tools/verify-hook-targets.py`, `tools/hookselftest.cpp` (28 проверок)
  и `tools/device-e2e.sh`.
* **v2.6.1** — переключатель для прогона альтернативного пути на ядре, где
  sdcardfs есть: файл `/data/adb/sdcardfs_restore.force_raw` заставляет
  `storage.sh` не поднимать sdcardfs и снять прежние маунты (см. §6.1). Ничего
  больше не менялось; на ядре без `CONFIG_SDCARD_FS` путь включается сам, без
  этого файла.
* **v2.6.0** — альтернативный путь без sdcardfs. Модуль пробует
  `/mnt/runtime/full/emulated`, проверяет тип ФС под точкой через `statfs` и при
  несовпадении откатывается на сырое `/data/media`; `storage.sh` в этом случае
  расставляет POSIX ACL с именованной записью для `AID_EVERYBODY` (9997) — access
  и default, чтобы `umask 0077` приложений не съедал групповые биты. Добавлена
  утилита `tools/storage-fix`. Проверка готовности основного пути переведена с
  `grep /proc/mounts` (видит маунты под точкой) и с `stat -f -c %T` (в окружении
  модулей KernelSU это busybox, который печатает `UNKNOWN`) на чтение
  `/proc/mounts` средствами шелла с выбором последней записи для пути.
* **v2.5.0** — упрощение до прямой функциональности. Удалены: `config` со всеми
  директивами (`!enabled`, `!android_dirs`, `!verbose`, `!selftest`, `!relabel`,
  `!relax`), вся диагностика (`logIdentity`, `logPathLadder`, `runMountProbes`,
  `dumpSelinuxDiagnostics`, `selftest`), второй уровень маунта с подменой
  личности через `setfsuid`/`setfsgid`/`setgroups`, запасной прямой маунт
  sdcardfs и `relax-storage.sh`. Проверено на устройстве, что всё удалённое не
  требуется: модуль работает с полными capabilities (`CapEff=0x1ffffffffff`),
  поэтому права DAC ему не мешают.
* **v2.4.0** — обработка `ANDROID_WRITABLE`: `Android/data` стал виден в
  системном приложении «Файлы».
* **v2.3.0** — доступ к корню `/storage/emulated` через перемаркировку
  `/data/media`.
